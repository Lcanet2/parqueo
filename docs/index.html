Workflows

Vos procédures, dessinées une fois. Appliquées à chaque ticket.

Un workflow démarre sur un déclencheur, puis enchaîne des blocs. Certains agissent — affecter, notifier, changer la priorité. D'autres attendent : le ticket se gare sur le bloc et ne repart que lorsque la condition est remplie. C'est ce qui fait la différence entre une règle d'automatisation ordinaire et une vraie procédure de service.

Déclencheurs

Le point de départ

Un ticket est créé, ou son statut change. Filtrez ensuite sur la catégorie, le formulaire d'origine, la priorité ou le statut atteint — un workflow par procédure, pas un fourre-tout.

Actions

Ce que l'application fait à votre place

Affecter une équipe ou une personne, ajuster la priorité et le statut, poster une note dans le fil, envoyer un email au demandeur ou à une adresse fixe, appeler un webhook.

Attentes & conditions

La procédure suit le rythme réel

Le bloc d'attente retient le ticket jusqu'à sa prise en charge ou jusqu'à un statut donné. Le bloc de condition ouvre deux chemins : urgence d'un côté, traitement normal de l'autre.

Affecter à une équipe Assigner à une personne Changer la priorité Changer le statut Ajouter une note Envoyer un email Webhook Condition oui / non Attendre la prise en charge Attendre un statut

Le bloc webhook ouvre la porte au reste de votre SI. Branchez n8n, Zapier ou votre propre script : création du compte dans l'annuaire, commande de matériel, alerte dans Teams. IT Desk envoie le ticket, votre automatisation fait le reste.

Le parcours d'un ticket

De la demande à la clôture, sans relance manuelle.

01

L'utilisateur demande

Trois portes d'entrée : le catalogue de demandes avec ses formulaires guidés, le ticket libre, ou un simple email à l'adresse du support — pièces jointes comprises. Avant de valider, la base de connaissances lui propose les articles de sa catégorie ; beaucoup de tickets s'arrêtent là.

02

Le workflow prend la main

Dans la seconde : affectation à la bonne équipe, priorité ajustée selon le formulaire, accusé de réception envoyé. Le ticket se gare ensuite sur le bloc d'attente jusqu'à ce qu'un technicien le prenne.

03

Le technicien traite

Un fil de discussion, des pièces jointes, et un journal d'événements horodaté qui garde trace de chaque changement de statut, d'assignation et de priorité. Le poste ou l'imprimante concernée est rattaché au ticket : l'historique du matériel se construit tout seul.

04

L'utilisateur donne son avis

À la résolution, une enquête de satisfaction en un clic — satisfait ou non. Assez court pour qu'on y réponde vraiment, assez pour savoir où le service se dégrade.

05

Le ticket se ferme seul

Un ticket résolu sans nouvelle activité se clôture automatiquement après le délai que vous fixez. Plus de file encombrée de tickets terminés que personne n'ose fermer.

Fonctionnalités

Tout le helpdesk, rien de superflu.

Chaque module est activable et se règle depuis l'administration — vous n'imposez à vos équipes que ce dont elles se servent.

Catalogue de demandes

Composez vos formulaires — texte, liste déroulante, date, case à cocher, champs obligatoires. Chaque formulaire porte sa catégorie, sa priorité, et peut déclencher son propre workflow.

Base de connaissances

Des articles courts rangés par catégorie, suggérés au moment où l'utilisateur rédige sa demande. Vos techniciens les écrivent eux-mêmes, sans passer par un admin.

Inventaire du parc

Postes, imprimantes, serveurs et logiciels : état, emplacement, date d'achat, détenteur. Chaque fiche liste les tickets du matériel, et l'import CSV évite la saisie initiale.

Collecteur email

Une boîte IMAP surveillée : chaque message devient un ticket, chaque réponse à une notification devient un commentaire. Vos utilisateurs peuvent ignorer le portail — ça marche quand même.

Connexion Microsoft Entra ID

SSO OpenID Connect avec votre annuaire, restriction par domaine email, comptes locaux en secours. Aucun mot de passe supplémentaire à distribuer.

Rôles, équipes et visibilité

Utilisateur, technicien, administrateur. Chacun ne voit que ce qui le concerne : ses demandes, la file de son équipe, ou l'ensemble du service.

Notifications email

À la création, au changement de statut, à l'assignation, à chaque commentaire — activables une par une pour éviter le bruit inutile.

Files de tickets lisibles

Filtres par statut, priorité, catégorie, équipe et assigné, recherche, pagination et export — la file quotidienne d'un technicien, pas un tableur.

Webhooks sortants

Chaque étape de workflow peut appeler une URL signée par un secret partagé, avec le contexte du ticket. De quoi relier IT Desk à ce que vous avez déjà.

Tableaux de bord modulaires

L'administrateur compose l'écran d'accueil de chaque rôle en posant des widgets sur une grille : tuiles de chiffres clés, répartition par statut, flux hebdomadaire créés / clôturés, charge par technicien, âge des tickets en attente, état du parc. Treize widgets, douze métriques, et la possibilité de laisser chacun réarranger le sien.

Déploiement

Sur votre serveur, avec vos données.

Une API Node.js, une base PostgreSQL, une interface React. Rien à envoyer chez un éditeur, rien à ouvrir sur l'extérieur si vous ne le souhaitez pas.

Schéma versionné — migrations Prisma, et un jeu de données de démonstration pour explorer avant de basculer.
Réglages en interface — priorité par défaut, délai de clôture automatique, notifications, enquête de satisfaction, visibilité du parc.
Comptes en masse — import CSV des utilisateurs et du parc, ou provisionnement au premier login SSO.
Pas d'agent à déployer — un navigateur suffit, sur poste comme sur mobile.
# récupérer et configurer
$ git clone https://github.com/Lcanet2/it-desk.git
$ cd it-desk/server && npm install
$ cp .env.example .env
 
# base de données + jeu de démonstration
$ npm run prisma:migrate
$ npm run seed
 
# c'est parti
$ npm run dev
